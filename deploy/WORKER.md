# STEMORA Worker บน Mac ของผู้ดูแล

เว็บสร้างคิวถาวรใน PostgreSQL และแอปบน Mac เชื่อมออก HTTPS เพื่อรับเพลงทีละงาน แยกด้วย MLX บน GPU ของ Apple silicon และเก็บโมเดลพร้อมใช้งานระหว่างเพลง มี Demucs/PyTorch CPU เป็นสำรอง แล้วส่ง PCM16 stereo 44.1 kHz กลับ private S3 ผ่าน API ของเรา ไม่มีบริการ AI inference ภายนอกและไม่เปิดพอร์ตบ้าน

## ติดตั้ง

เครื่องนี้เป็น Apple M5 / RAM 16 GB; แอปรุ่นแรกสำหรับ macOS 14 ขึ้นไปบน Apple silicon ต้องมี uv, FFmpeg และ Swift toolchain สำหรับ build เท่านั้น

```bash
python3 worker/install_macos.py
```

แอปอยู่ที่ `~/Applications/STEMORA Worker.app` ส่วน runtime, config, สถานะ และ log อยู่ที่ `~/Library/Application Support/STEMORA Worker/` โปรแกรมที่ติดตั้งทำงานได้โดยไม่ต้องเปิดโปรเจกต์ใน editor
config มี token เฉพาะเครื่อง mode 600 ไม่ใส่ Git/แชต/ภาพหน้าจอ ส่วน VPS เก็บเฉพาะ SHA-256 ผ่าน `scripts/manage_workers.py enroll --id UUID --token-hash SHA256 --name NAME` รันด้วย environment ของ backend

เปิด `STEMORA_WORKER_ENABLED=1` ใน `.env` บน VPS แล้ว recreate backend ด้วย Compose ทั้งสองไฟล์ตาม PRODUCTION.md เปิดแอปและเลือกเปิดรับงาน
แอปเริ่มต้นแบบพักรับงานเพื่อให้ลงทะเบียนเครื่องก่อน มีตัวเลือกเวลา, พักหลังงานปัจจุบัน และเปิดพร้อม login ซึ่งปิดอยู่จนเจ้าของเลือกเอง
เมื่อเปิดรับงาน โปรแกรมป้องกัน idle sleep เฉพาะช่วงรับงาน/ทำงาน เมื่อพักหรือออกจะคืนค่าโดยไม่แก้ Power settings ถาวร การพับฝาเครื่อง ปิดเครื่อง หรือสั่ง Sleep เองยังทำให้บริการหยุดรับงานได้

## คิวและสิทธิ์

- `workers` เก็บเครื่องที่ผู้ดูแลลงทะเบียนและเพิกถอนได้; `stem_jobs` เก็บ spec/status/result ใน PostgreSQL และรวมใน backup/portable snapshots
- ลูกค้ายังใช้ cookie + CSRF เดิม; `/api/worker/` ใช้ bearer ของเครื่องอย่างเดียว ไม่รับ cookie แทน และส่งเพลงได้เฉพาะงานที่ถือ lease อยู่
- Worker ไม่ได้สิทธิ์ DB หรือ S3 โดยตรง ไม่รับ URL/คำสั่ง shell/model path จากผู้ใช้ ใช้ endpoint และชนิดงานที่กำหนดไว้
- คอมเชื่อมออก HTTPS/SNI ตามโดเมน ตรวจใบรับรองตามปกติทุกครั้ง; `origin_ip` เลือกเชื่อมเครื่อง 143 โดยยังตรวจ hostname เพื่อหลีกเลี่ยง bot challenge ที่ไม่เหมาะกับ machine API และไม่ส่ง bearer ตาม HTTP redirects
- งานสูงสุด 10 ต่อบัญชี, source สูงสุด 50 MB/10 นาที; จองพื้นที่ต้นฉบับชั่วคราวและผลลัพธ์ในโควตา 200 MB ตั้งแต่เข้าคิว แล้วคืนพื้นที่ต้นฉบับเมื่อจบ/ยกเลิก
- ส่งผลชิ้นละไม่เกิน 4 MB พร้อม offset/retry ตรวจ WAV/duration ก่อน commit; commit ซ้ำไม่สร้างไฟล์ซ้ำ และสร้าง ZIP ชั่วคราวเมื่อลูกค้าดาวน์โหลด
- Worker ต่อ heartbeat ทุก 20 วินาที, lease 180 วินาที; lease หมดอายุจะเข้าคิวใหม่ สูงสุด 3 ครั้ง งานเก่าไม่มีสิทธิ์ส่งผลหลังเปลี่ยน lease
- การรีสตาร์ต backend ไม่ทำให้คิว worker หาย; ลูกค้ากลับเข้าระบบหรือเปิดจากงานแยกเสียงเพื่อรับผลได้
- ปุ่มยกเลิกคืนพื้นที่จองและปิด lease; worker หยุด subprocess เมื่อได้รับสถานะ lease หมดสิทธิ์หรือ heartbeat ขาดนานกว่า 90 วินาที

## GPU และข้อจำกัด

รุ่นปัจจุบันติดตั้ง `runtime-mlx` แยกจาก `runtime` สำรอง เพื่อแยก NumPy/dependencies ตั้ง `backend=mlx`, `mlx_python` เป็น Python ของ runtime ใหม่ และ `device=cpu` สำหรับสำรอง โมเดลมาตรฐานและ FT ดาวน์โหลดครั้งแรกตอนติดตั้งและตรวจขนาด/SHA-256 ตรงกับ registry ที่ pin ไว้แล้ว ตัวประมวลผล MLX ปิดการดาวน์โหลดระหว่างรับงาน
ตัวเลือกคุณภาพในแอปมี มาตรฐาน (`htdemucs`) และ ละเอียด (`htdemucs_ft`); ใช้กับงานที่ยังไม่มีผลแยกพร้อมส่ง ไม่เปลี่ยนผลของงานที่กำลังทำหรือผล cache ที่ตรวจผ่านแล้ว หน้าเว็บลูกค้าไม่แสดงชื่อโมเดล
MLX helper เป็น subprocess ส่วนตัวผ่าน stdin/result file ไม่มี network listener และไม่รับโมเดลหรือคำสั่ง shell จากลูกค้า เก็บ Separator หนึ่งตัวระหว่างเพลง เปลี่ยนโมเดลเมื่อเปลี่ยนโหมด กำหนด MLX buffer cache 512 MiB; หน่วยความจำรวมจริงสูงกว่านี้เพราะรวม weights/activations

ข้อจำกัดเส้นทาง PyTorch สำรองจากการทดสอบรุ่นแรก:

เลือก CUDA/MPS เมื่อพร้อม และลอง CPU หากโมเดลรันบน GPU ไม่สำเร็จ; PyTorch 2.5.1 บาง operation บน MPS อาจต้อง CPU จึงยังไม่รับประกันความเร็วจากชื่อชิป ต้อง benchmark เพลงจริงก่อนเปิดรับงานมาก
เริ่มทีละหนึ่งเพลง ตั้ง timeout 30 นาทีต่อการรัน เมื่อเครื่องหลับ/ปิด/เน็ตขาด ลูกค้าจะเห็นงานรอในคิว เปิดเครื่องเสียบไฟและอินเทอร์เน็ตไว้ขณะให้บริการ
รุ่นแรกยังไม่เก็บ checkpoint ระหว่าง inference; งานที่ขาดการเชื่อมต่อเริ่มแยกใหม่ได้โดยไม่คิด quota ผลลัพธ์ซ้ำ
`/api/health` แสดงเฉพาะความพร้อมของ worker ไม่เผยชื่อเครื่อง token หรือรายละเอียดลูกค้า

## ส่งผลต่อหลังเน็ตหลุด

ผล canonical WAV และ checksum อยู่ใน `~/Library/Application Support/STEMORA Worker/results/<task UUID>/` ซึ่งเข้าถึงได้เฉพาะบัญชีเครื่องนี้ เก็บผลก่อนเริ่ม upload และตรวจ source hash/mode/checksum ก่อนใช้ซ้ำ เมื่อโปรแกรมเปิดใหม่หรือได้รับ lease ใหม่ของงานเดิมจะส่งผลที่เก็บไว้ ไม่เรียก inference ซ้ำ
เมื่อ lease ยังเดิม ใช้ offset ที่ server ยืนยันแล้ว; เปลี่ยน lease จะส่งไฟล์ใหม่ตั้งแต่ offset 0 ให้ staging ใหม่ โดยยังใช้เสียงที่แยกไว้เดิม การส่งที่ไม่ได้รับ ack สามารถ replay bytes/offset เดิมได้
ลองเชื่อมต่อซ้ำขณะ lease ยังใช้ได้ โดยแต่ละช่วงรอไม่เกินประมาณ 5 นาที เมื่อหยุด/หมดสิทธิ์จะเก็บผลและคืนคิวตามกลไกเดิม งานที่แยกไม่เสร็จยังเริ่ม inference ใหม่ หลัง server ยืนยัน complete จึงลบ cache ของงาน
ตรวจล้าง cache เก่าขณะรับงานใหม่: อายุเกิน 24 ชั่วโมง หรือ cache งานอื่นรวมเกิน 800 MB จะลบรายการเก่าก่อน ไม่ลบงานปัจจุบัน จึงอาจยังมีไฟล์เก่าขณะไม่มีงานใหม่เข้ามา ผลที่ยกเลิกจะถูกล้างตามรอบนี้เช่นกัน

## ผลตรวจ MLX บน Mac M5 / RAM 16 GB

- เสียงสังเคราะห์ stereo 16 วินาที, htdemucs, shifts=1: CPU inference 4.986/4.405 วินาที; MLX 7.717/0.591 วินาที (รอบแรก/รอบถัดไป) รวม model load แยกจากตัวเลขนี้ โหมด FT บน MLX 2.497/2.437 วินาที การเตรียม GPU ครั้งแรกอาจช้ากว่า CPU
- เว็บ production รับงานจริงจาก HTTPS และ Mac แสดง device=mlx: มาตรฐาน task `a1a10d12-c40a-43de-9e50-5e77d84dd0fe` จบใน 17.164 วินาที; ละเอียด task `b7bdeda8-91d9-46ac-96d4-4d18d9fc56cf` จบใน 19.915 วินาที รวมรับ–ส่ง Cloud
- ทั้งสองโหมดได้ 4 WAV stereo PCM16 44.1 kHz/16 วินาที, ZIP CRC/bytes ตรง และ quota เพิ่ม 11,289,776 bytes ต่อหนึ่งงาน ไม่เก็บ ZIP ซ้ำ คืน source/reservation แล้ว
- จำลองขาดการเชื่อมต่อหลังส่ง stem แรก แล้วสร้าง Worker ใหม่: ได้ผลจาก cache ส่งต่อครบ 4 แทร็ค bytes ตรงกัน ไม่เรียก inference ซ้ำ และลบ cache หลัง commit
- ชุด regression 57 tests ผ่าน 56 / ข้าม 1 ที่ต้องใช้ PostgreSQL แยก; transport/cache 8 tests ผ่าน ภาพแอป `docs/screenshots/stemora-worker-mlx.png`
- ตัวเลขนี้เป็นเสียงสังเคราะห์สั้น ไม่มีการวัด SDR กับ ground truth เพลงจริงหรือการฟังเทียบหลายแนว จึงยังไม่รับรองว่าโหมดละเอียดดีกว่าทุกเพลง และไม่ใช้ตัวเลขนี้รับประกันเวลาเพลงเต็ม

## การดูแล

พักรับงานจากแอปก่อนปิดเครื่อง งานปัจจุบันจะทำต่อจนเสร็จ การกดออกจะหยุดงานและคืนคิวตาม lease ไม่ลบเพลงผู้ใช้
เพิกถอนเครื่องด้วย `scripts/manage_workers.py revoke --id UUID` โดยรันใน backend environment
เก็บ token/raw config ไว้เฉพาะเครื่องผู้ดูแล; backup ฐานข้อมูลมี token hashes และข้อมูลส่วนตัวจึงคงสิทธิ์ mode 600 เช่นเดิม

## ปรับการเชื่อมต่อ 30 ตุลาคม 2026

พบ TCP connect timeout ขณะส่งผลกลับ Cloud หลุดนอกขอบเขต retry ทำให้งานถูก release และเริ่ม inference ใหม่ แก้ให้ TCP/TLS establishment อยู่ใน retry เดียวกับ request แล้ว การส่งซ้ำใช้ bytes/offset เดิมและยังตรวจ lease ตามปกติ จำกัด 3 ครั้งก่อนคืนคิว กรณีอินเทอร์เน็ตขาดนานยังอาจต้องเริ่มงานใหม่
แอปแสดงขั้นเตรียมไฟล์/ส่งกลับ/บันทึกผลแยกจากการประมวลผล พร้อม progress ระหว่างอัปโหลด
เครื่อง M5 นี้ตั้ง device=cpu ตามเส้นทางที่ทดสอบผ่าน เพื่อลดการลอง MPS ที่ไม่สำเร็จทุกเพลง ตั้งกลับ auto ได้เมื่อทดสอบ runtime/GPU รุ่นใหม่
ตรวจ transport timeout/replay/lease rejection 4 tests ผ่าน และแยกเสียงจริงด้วย runtime อิสระ 1 วินาที 2 stems พร้อมบันทึก Cloud ผ่านใน 8.98 วินาที
